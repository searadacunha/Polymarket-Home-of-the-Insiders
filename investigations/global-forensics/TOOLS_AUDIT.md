# Tools audit: external repositories for Polymarket on-chain forensics

Date: 2026-11-02. Method: read only, `gh api` (contents, trees, commits, license endpoints) and public web pages. Nothing was cloned, installed or executed. Repository content was treated as data. Full 40-character SHAs are the head of the default branch at audit time. "Tests" means a test directory or test files exist in the tree, not that they pass. Licenses come from `gh api repos/OWNER/REPO/license` (SPDX as GitHub detects it), then compared with pyproject, package.json or LICENSE files.

Our engine is stdlib Python, so the bar for ADOPT is low dependency weight, a clear license and a method we lack. Most rows are REFERENCE ONLY: we read the method and re-implement it.

## Per-repository notes

### enviodev/hypersync-client-python
Read: `examples/wallet.py`, `README.md`, `test.py`, root listing.
- `wallet.py` raises ValueError unless `ENVIO_API_TOKEN` is set, and builds `ClientConfig(url="https://eth.hypersync.xyz/", bearer_token=...)`. README says "An API token is required to use HyperSync". This agrees with the 401 you measured.
- It does not cover traces. The query has only `LogSelection` (ERC20 Transfer topic0 `0xddf252ad...`, address padded into topic1 or topic2) and `TransactionSelection(from_=..., to=...)`, with a `FieldSelection` of block, log and transaction fields. No `TraceSelection`. The README says the library can query traces, and `test.py` imports `TraceField`, but the wallet example does not use them.
- Method we lack: one query that joins logs (both directions via topics) and native transactions by address from block 0, with the node-side implicit join returning the transactions and blocks of matching logs.
- Flaws: runs `collect` once and prints `res.next_block` without looping, so output can be partial. Volume sums mix tokens ("meaningless" per its own comment) and add `value` to both sender and recipient, so it is gross volume, not net flow. No tests, only `test.py` benchmark.

### PatrickMockridge/chainlens
Read: `src/chainlens/tracing/tracer.py` (546 lines), `src/chainlens/ledger/walk.py` (789 lines), `src/chainlens/analysis/clustering.py`, `src/chainlens/analysis/heuristics/eth_deposit.py`, `pyproject.toml`. MIT; deps: httpx, hishel, tenacity, pydantic, anyio, rustworkx, jinja2.
- Method that matches our need: every way a walk ends is a named stop reason counted in `stop_reasons` (`budget_depth`, `budget_nodes`, `budget_edges`, `budget_time`, `policy_max_fan_out`, `no_history`, and `frontier_deferred` in `walk.py`), and `FlowGraph.truncated` is set whenever the budget, not the graph, ended the walk. `walk.py` explicitly separates "frontier" (not truncation) from truncation. This is the same discipline as our tracer stop for each unfollowed branch; compare its counters with ours.
- `clustering.py`: union-find where every merge carries evidence, conflicting high-confidence evidence refuses a merge, and cluster confidence is the minimum over its merges (not the mean). Entity ids derive from membership, so runs are reproducible. This is a concrete rule our graph.py layers could take.
- `walk.py`: unknown amounts stay `None`, totals are `None` rather than a partial sum, nothing is apportioned.
- `eth_deposit.py` flaws: it skips zero-value transactions (`if not transaction.value: continue`), so ERC20 deposits (USDC, pUSD) are invisible to it; it requires 3 or more distinct senders (`minimum_senders=3`) and exactly one forward destination in the transactions it was given, so a truncated history gives false merges or misses; confidence is a made-up linear ramp (0.4 plus 0.05 per sender, cap 0.9). Its own docstring says it needs corroboration.
- Tracer built on `ADDRESS_TXS` capability, per address; it will not scale to a heavy exchange address without our block-cursor approach.

### gl0bal01/chainmap
Read: `src/peelChain.js`, `src/roundTrips.js`, README, `package.json`, tree. MIT.
- Cycles: Tarjan SCC over the sampled graph; any node in an SCC of size above 1, or a self loop, is flagged. Correct and tiny. It ignores time order and amount, so an A to B and B to A pair weeks apart counts the same as a same-day round trip.
- Peel chains: nodes with exactly one distinct sender and one distinct recipient, forwarded amount between `keepRatio` 0.9 and `slack` 1.1 of received, time not decreasing, no revisit. It uses `amountText` ("nominal per-token magnitude, NOT fiat-normalized"), so mixed tokens are compared raw. The 1.1 slack lets a node forward more than it received, which is not a peel.
- README admits overlays "only ever see the sampled graph, never full on-chain history". Uses Etherscan v2 with a user key.
- Take from it: the idea of reporting cycle membership, with time and amount constraints added by us.

### pselamy/polymarket-insider-tracker
Read (all under `src/polymarket_insider_tracker/`): `ingestor/observation_boundary.py`, `ingestor/v2_cursor_walk.py`, `ingestor/trade_poller.py`, `profiler/funding.py`, `profiler/_funding_rpc.py`, `detector/sniper.py`, `endpoints.py`. MIT; the pyproject has no license field.
- Strong part: a durable "complete-through" boundary. A page only advances the checkpoint if it passes two tests (`ProofResult.proven = reach and continuity`): it reaches back to the stored boundary, and every identity between is accounted for. Failures become `LossEvent` records with reasons `horizon-expired`, `restart-beyond-horizon`, `continuity-mismatch`; the checkpoint, identities, trim and loss events are written in one Redis MULTI/EXEC. `v2_cursor_walk.py` caps a cycle at 20 pages and 20,000 rows (`MAX_WALK_PAGES`, `MAX_WALK_ROWS`), and `possible_data_loss` is true if a non-empty walk stops on exhaustion or the page limit without proof. This is the proof model we want for Polymarket data-api windows. The source id is `sha256("<url>|<coverage>")[:12]`.
- `endpoints.py`: `OFFICIAL_V1_TRADES_URL = "https://data-api.polymarket.com/trades"`, `OFFICIAL_V2_TRADES_URL = "https://data-api.polymarket.com/v2/trades"`, `V1_RETIREMENT_DATE = "2026-10-24"`. If any of our code still calls `/trades`, check it.
- Window limit that confuses "first transaction found" with first historical (confirmed): `funding.py` `get_first_usdc_transfer` calls `_get_transfer_logs(limit=1)` and returns the first log. The scan covers only `latest - max_lookback_blocks`, where `DEFAULT_MAX_LOOKBACK_BLOCKS = 80_000` (comment: about 44 hours at 2 s blocks, "fits inside the pruned-history horizon of most public RPCs"), in chunks of `DEFAULT_CHUNK_SIZE_BLOCKS = 9_000`. So "first USDC transfer" is the oldest one within about 44 hours, not the wallet's first ever. Also any exception in `_get_first_token_transfer` is logged and returns `None`, so an RPC failure looks like "no funder". Only the two USDC contracts (bridged and native) are tracked, not pUSD. The docstring rationale is that fresh wallets are new by definition, which is the unproven assumption.
- `sniper.py`: DBSCAN (eps 0.5, min_samples 2) on features [md5-of-market-id mod 1000 / 1000, entry delta in hours, log10 size]. The hashed market id is a meaningless Euclidean axis; entry delta in hours spans 0 to 0.083 so size dominates the distance. Weak statistics; do not import.

Message layouts (byte index):
- v1 Message: version 0 (4), sourceDomain 4 (4), destinationDomain 8 (4), nonce 12 (8, uint64), sender 20 (32), recipient 52 (32), destinationCaller 84 (32), messageBody 116.
- v1 BurnMessage: version 0, burnToken 4, mintRecipient 36, amount 68, messageSender 100, total length 132.
- v2 Message: version 0, sourceDomain 4, destinationDomain 8, nonce 12 (bytes32), sender 44, recipient 76, destinationCaller 108, minFinalityThreshold 140 (4), finalityThresholdExecuted 144 (4), messageBody 148.

Key fact for proof.py and bridges.py: in v2 the source message is built with `EMPTY_NONCE = bytes32(0)` and `EMPTY_FINALITY_THRESHOLD_EXECUTED = 0` (`MessageV2.sol`), and the real nonce is set when attested. So the nonce in the destination `MessageReceived` cannot be read from the source `MessageSent` bytes; matching a v2 burn to a mint needs the attestation service or matching on the other fields (domain, sender, recipient, amount, hook data, timing). That is a stop to record, not a link to invent. v1 nonce is on the source event, so v1 matching is exact (domain plus nonce).
Domain ids and contract addresses are not in this repo as I read it (not confirmed).

## Order book archives

Context: Polymarket does not serve historical order books. The CLOB `/book` returns the current state only, so any L2 history is third-party capture. Several search results state this (Apify dirtycode actor page, a vendor article); I did not verify it on Polymarket's own docs.

- PMXT archive (`archive.pmxt.dev`): confirmed by the public scraper repo `LoveTyrant/lt-pmxt-scraper` (MIT, pushed 2026-05-28), which scrapes it. Listing pages: `/Polymarket/v1`, `/Polymarket/v2`, `/Kalshi`, `/Limitless`, `/Opinion`. Files are hourly `.parquet` order book snapshots, one listing line per file with size (example in the scraper comment: 748.9 MB, dated 06 Apr 2026 23:00 UTC), stored on Cloudflare R2 hosts `r2.pmxt.dev` (v1) and `r2v2.pmxt.dev` (v2). The scraper has no key setting in its config, which suggests keyless download, and the README warns that older hourly files are backfilled and can grow after publication. Not confirmed: the date range (earliest and latest file), the data license or terms of use, the parquet schema, and live availability. My direct fetches of `archive.pmxt.dev` timed out and the fetch tool got connection refused; `r2v2.pmxt.dev/` returned HTTP 404 on its root, which only shows the host answers. The `pmxt-dev/pmxt` repo (MIT, pushed 2026-09-30) is a library, and I found no archive documentation in its tree. A mirror's description mentions "MIT-ext", not verified.
- Vike Data: not confirmed. No GitHub repository and no web result for "Vike Data" with Polymarket.
- Pendulum Flow: not confirmed. No GitHub repository and no web result.
- Other public Polymarket history or order book sources that web search surfaced (names and claims from search summaries only, not checked): PolyOrderbooks (independent archive, L2 depth, 1 second resolution, MCP server and PyPI package `polyorderbooks`), Telonex (tick level, claims 3+ years, "Free Downloads" page), Oddpool (data from 2026-03-20), Predexon (per-token L2 snapshots from 2026-01-01), Hugging Face dataset `trentmkelly/polymarket_historical_data` (zstd parquet, does not appear to include depth), an Apify actor (paid per snapshot), and an arXiv paper using 52 days (2026-02-21 to 2026-04-15) of tick data. License, keys and ranges of these are not confirmed.
- Practical note: even if PMXT is reachable, hourly snapshots cannot reconstruct a fill-by-fill book, and nothing before the capture start exists. Use it for context around known trades, not as proof of a book state at a trade time.
